Chapter 34

Drivechains

BIP-300/301: Anatomy of a Failed Proposal

Drivechains proposed an alternative to federated sidechains: let Bitcoin miners themselves custody the two-way peg. Through "hashrate escrow," miners would collectively control sidechain withdrawals, with only one new opcode (OP_DRIVECHAIN) plus a small set of new coinbase-message rules. The proposal never achieved consensus, and in 2026 its principal advocate announced an exit hard fork instead. We study it anyway—and partly for that reason: drivechains are this book's best case study in how a technically coherent proposal can fail on its security model, its trust assumptions, and the governance process of Chapter 33, and in what an exit from that process looks like. The mechanism first; the cautionary tale at the end (Section 34.7).

34.1 The Drivechain Vision

Definition 34.1 (Drivechain)

A drivechain is a sidechain where:

  • Bitcoin miners validate sidechain withdrawals
  • No trusted federation required
  • Sidechains can have arbitrary rules (smart contracts, privacy, etc.)
  • BTC moves between chains via "hashrate escrow"

Definition 34.2 (Hashrate Escrow)

Hashrate escrow (BIP-300) is a withdrawal mechanism where:

  1. Withdrawal requests are published on the sidechain
  2. Miners vote on withdrawals via coinbase outputs
  3. Withdrawals require ~3-6 months of miner ACKs
  4. Funds release only after threshold reached

34.2 BIP-300: Hashrate Escrow

Definition 34.3 (BIP-300 Mechanism)

BIP-300 introduces OP_DRIVECHAIN for withdrawal voting: 

Sidechain deposit address:
  OP_DRIVECHAIN <sidechain_id> OP_TRUE

Withdrawal process:
  1. User requests withdrawal on sidechain
  2. Sidechain bundles requests into withdrawal bundle
  3. Bundle hash published to mainchain
  4. Miners ACK/NACK in coinbase; bundle needs 13,150 ACKs
     within a 26,300-block (~6-month) window
  5. If ACKs > threshold, withdrawal executes

Definition 34.4 (Withdrawal Bundle)

A withdrawal bundle (historically written WT^; current BIP-300 simply says "bundle", capped at 6,000 withdrawals) aggregates multiple withdrawals:

  • Created by sidechain nodes
  • Contains destinations and amounts
  • Single mainchain transaction when approved
  • Batching reduces on-chain footprint

Remark 34.1 (Withdrawal Security)

For a withdrawal to be stolen, miners must:

  1. Create a fraudulent withdrawal bundle
  2. Accumulate 13,150 ACKs within the 26,300-block (~6-month) window. With other miners abstaining, a bare majority takes ~6 months and ~3 months requires near-unanimous ACKing; if defending miners actively NACK (the score moves +1/0/−1 per block), the coalition needs about 75% of blocks to reach the threshold inside the window at all
  3. Maintain >50% hashrate commitment throughout

The extended timeframe allows users to detect and respond to theft attempts.

34.3 BIP-301: Blind Merged Mining

Definition 34.5 (Blind Merged Mining)

Blind Merged Mining (BMM) allows sidechain blocks to be mined without miners running sidechain software:

  1. Sidechain node creates block, computes header hash
  2. Node pays Bitcoin miner (via mainchain) to include hash
  3. Miner includes hash in coinbase without validating sidechain
  4. Sidechain accepts block if hash is in valid Bitcoin block

Remark 34.2 (BMM Properties)

Blind merged mining provides:

  • No miner overhead: Miners don't run sidechain nodes
  • Permissionless: Anyone can pay for block inclusion
  • Fee market: Sidechain block space has its own market
  • Inherited security: Sidechain blocks anchored to Bitcoin PoW

Example 34.1 (BMM Transaction)

// Sidechain operator creates BMM request
BMM Request:
  - Sidechain ID: 1
  - Block hash: 0xabc123...
  - Fee to miner: 0.001 BTC

// Miner includes in coinbase
OP_RETURN <BMM_TAG> <sidechain_id> <block_hash>

// Sidechain accepts if:
// 1. Hash matches sidechain block
// 2. Bitcoin block is valid and in best chain

34.4 Security Analysis

Remark 34.3 (Drivechain Trust Model)

Drivechains are secured by:

  • Miner honesty: Majority of hashrate must be honest
  • Time delay: ~3-6 months to complete theft
  • Public visibility: Theft attempts are observable
  • Economic incentives: Theft risks Bitcoin's value

A second trust vector is easy to miss. Bitcoin's consensus does not validate sidechain state, so each sidechain's rules—including what counts as a legitimate withdrawal—are defined entirely by whoever maintains that sidechain's software (in practice, the sponsoring company for every drivechain proposed to date). By the code-as-specification argument of Section 33.9, those maintainers hold de facto rule-setting power over deposited funds: a malicious or compromised release can redefine peg behavior, and miners voting on withdrawal bundles have no Bitcoin-level criterion for distinguishing legitimate bundles from illegitimate ones. Users of a drivechain therefore trust two parties the base layer never asks them to trust: a miner majority and a software maintainer.

Definition 34.6 (Miner Theft Attack)

A miner theft attack on drivechains:

  1. Malicious miners create false withdrawal to themselves
  2. Vote for it over ~3-6 months
  3. If successful, steal all sidechain deposits

Cost: Must maintain >50% hashrate for 3-6 months while the attack is visible.

Remark 34.4 (Attack Economics)

The economic argument for drivechain security:

  • Stealing sidechain funds would damage Bitcoin's reputation
  • Miners have large investments in Bitcoin-denominated equipment
  • Rational miners won't destroy their own revenue source
  • 3-month visibility allows market/social response

Counter-argument: miners could steal and exit if theft value > future mining revenue.

Theft speed Instant (if colluding) ~3-6 months

34.5 The Drivechain Controversy

Drivechains are among the most contentious Bitcoin proposals.

34.5.1 Arguments For

Remark 34.5 (Pro-Drivechain Arguments)

  • Permissionless innovation: Experiment without risking mainchain
  • Absorb altcoin demand: Features as sidechains, not competitors
  • No federation: More decentralized than Liquid
  • Opt-in: Only users who want sidechains are exposed
  • Miner revenue: Additional fee income from BMM

34.5.2 Arguments Against

Remark 34.6 (Anti-Drivechain Arguments)

  • Miner incentives: Gives miners new power over user funds
  • MEV concerns: Miners could extract value via sidechain ordering
  • 51% attack surface: Reduces cost of certain attacks
  • Complexity: Adds significant consensus complexity
  • Ossification: Major change to Bitcoin's security model

Remark 34.7 (The MEV Concern)

With drivechains, miners gain new extractable value:

  • Sidechain transaction ordering (via BMM)
  • Withdrawal censorship or delay
  • Front-running sidechain DeFi (if applicable)

Critics argue this creates perverse incentives absent in Bitcoin today.

34.5.3 Technical Criticisms

Remark 34.8 (Specific Concerns)

  • Withdrawal time: 3-6 months is impractical for most users
  • Capital lockup: Funds stuck during withdrawal
  • Sidechain failure: If sidechain dies, withdrawals may be impossible
  • Coordination: Miners must coordinate voting (potential centralization)

34.7 Postscript: Activation Failure and the Exit Fork

Remark 34.9 (How the Proposal Ended)

BIP-300/301 were fully specified, implemented in a Bitcoin Core fork, and advocated for the better part of a decade—and never approached the rough consensus (Definition 33.4) that activation requires. The objections that stuck were the ones analyzed above: the security model asks users to trust a miner majority with custody (Definition 34.6) and a software maintainer with the rules (Remark 34.3), and many reviewers judged "miners can vote to take the deposits, slowly and in public" to be a description of the design rather than an attack on it.

Remark 34.10 (The 2026 "eCash" Fork)

In April 2026 the proposal's architect announced the exit: a hard fork of Bitcoin, named "eCash," scheduled for August 2026 at approximately block 964,000, with drivechains enabled natively. The fork copies Bitcoin's ledger and credits BTC holders 1:1 on the new chain—with one exception that drew immediate criticism: part of the balances associated with Satoshi-era addresses (roughly 500,000 of 1.1 million coins, per the announcement) would be reassigned on the forked ledger to investors who fund the project. No bitcoin moves—Chapter 26's taxonomy applies, and the BTC ledger is untouched—but every prior fork in Chapter 27, whatever its other choices, preserved existing balances exactly (even Bitcoin Gold's premine was newly mined, not reassigned). Critics called the reallocation confiscation; the project framed the fork as both an alternative path and pressure on Bitcoin Core, to be called off if BIP-300/301 activated first. (This "eCash" is unrelated to eCash/XEC, the 2021 Bitcoin ABC rebrand of Section 27.6.3.)

Remark 34.11 (The Cautionary Tale)

Read as a case study, the drivechain decade illustrates three of this volume's themes at once. First, technical coherence does not entitle a proposal to activation: the mechanism worked as specified, and the network declined it anyway, on trust-model grounds (Section 33.3's consensus formation operating as designed). Second, exit is always available—but Chapter 26's game theory governs what exit is worth, and Chapter 27's record of forks asserting themselves against the incumbent network effect is not encouraging. Third, the form the exit took—reassigning dormant balances to fund the venture—shows why the credibility of "your balances survive every rule change" is itself part of what a fork is selling, and what abandoning it costs.
