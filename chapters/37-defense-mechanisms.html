Chapter 37

Defense Mechanisms

Checkpoints, Confirmations, and Protection

Bitcoin has evolved multiple layers of defense against the threats described in the previous chapter. Some are built into the protocol, others are social or economic. This chapter examines confirmation requirements, checkpoints, node hardening, and the broader security model that protects Bitcoin users.

37.1 Confirmation-Based Security

Definition 37.1 (Confirmation)

A transaction has k confirmations when it is included in a block with k − 1 blocks built on top of it. The first block containing the transaction is confirmation 1.

Remark 37.1 (Confirmation Security Model)

Confirmations provide probabilistic security:

  • More confirmations = exponentially lower reversal probability
  • Against an attacker with hashrate q < 50%, the reversal probability is given by Nakamoto's formula (Theorem 36.1); it decays roughly geometrically in k, but the naive catch-up bound (q/(1−q))ᵏ understates it (q = 10%, k = 6: about 0.02%, not 0.0002%)
  • 6 confirmations (~1 hour): Standard for large transactions
  • 1 confirmation (~10 min): Often sufficient for small amounts

Example 37.1 (Industry Standards)

Amount/Risk Confirmations Rationale
Small (<$1000) 1-2 Attack cost > value
Medium ($1K-$100K) 3-6 Standard security
Large (>$100K) 6-12 High-value protection
Exchange deposits 2-6 Balance speed/security

37.2 Checkpoints

Definition 37.2 (Checkpoint)

A checkpoint is a hardcoded (block height, block hash) pair in node software. The node rejects any chain that doesn't include the checkpoint block.

Definition 37.3 (Historical Checkpoints)

Bitcoin Core historically included checkpoints: 

// From chainparams.cpp (historical)
checkpointData = {
    {11111,  "0x0000000069e244f73d78e8fd29ba2fd2..."},
    {33333,  "0x000000002dd5588a74784eaa7ab0507a..."},
    {74000,  "0x0000000000573993a3c9e41ce34471c0..."},
    {105000, "0x00000000000291ce28027faea320c8d2..."},
    // ... more checkpoints
};

Remark 37.2 (Checkpoint Security)

Checkpoints provide:

  • DoS protection: Reject low-work fake chains quickly
  • Deep reorg prevention: Cannot reorg past checkpoint
  • Sync speedup: Skip some validation before checkpoint

Tradeoff: Requires trusting checkpoint authors.

Remark 37.3 (Checkpoint Controversy)

Checkpoints are controversial because they:

  • Add trust in developers who set them
  • Could theoretically be used maliciously
  • Contradict "don't trust, verify" ethos

Modern Bitcoin Core has de-emphasized checkpoints in favor of:

  • AssumeValid: Skip signature verification before known block
  • Headers-first sync: Verify PoW chain before downloading
  • Minimum chain work: Reject chains below threshold

37.3 Minimum Chain Work

Definition 37.4 (Minimum Chain Work)

nMinimumChainWork is a hardcoded minimum cumulative proof-of-work a chain must have to be considered valid: 

// Approximate minimum chain work (increases with each release)
nMinimumChainWork = 0x0000000000000000000000000000000000000000
                    7f0000000000000000000000;

Chains below this threshold are rejected without full validation.

Remark 37.4 (Minimum Work Protection)

Minimum chain work provides:

  • Protection against low-work attack chains
  • Faster sync (reject obviously fake chains early)
  • No checkpoint-style trust (only requires past work exists)

An attacker must match the minimum work to even be considered.

37.4 AssumeValid and AssumeUTXO

Definition 37.5 (AssumeValid)

AssumeValid skips signature verification for blocks before a known "valid" block:

  • Still validates all other consensus rules
  • Still builds UTXO set
  • Just skips signature checks (most CPU-intensive part)
  • Can be disabled with -assumevalid=0

Definition 37.6 (AssumeUTXO)

AssumeUTXO allows instant sync by assuming a UTXO set snapshot is valid:

  1. Download UTXO snapshot (serialized state)
  2. Verify hash matches hardcoded value
  3. Begin syncing from snapshot height immediately
  4. Background-validate full history eventually

37.5 Node Hardening

Definition 37.7 (Eclipse Attack Mitigations)

Bitcoin Core includes multiple eclipse attack defenses:

  • Bucketed peer storage: Peers stored in buckets by IP range
  • Outbound diversity: Connect to different /16 networks
  • Anchor connections: Remember peers across restarts
  • Feeler connections: Periodically test new peers
  • Peer eviction logic: Protect diverse, long-standing connections

Definition 37.8 (Tor and Privacy)

Running over Tor provides additional protection:

  • IP address hidden from peers
  • Harder to target specific node
  • Onion-only mode possible (-onlynet=onion)

Tradeoff: Latency increase, potential Tor-level attacks.

37.6 Economic Security

Remark 37.5 (Security Budget)

Bitcoin's security is funded by:

Security Budget = Block Subsidy + Transaction Fees

This budget pays miners to provide honest hashrate, making attacks expensive.

Definition 37.9 (Attack Cost Asymmetry)

A key security property: attacking costs more than defending because:

  • Attacker must match honest hashrate + some margin
  • Attacker pays for hardware, electricity, opportunity cost
  • Honest miners are paid (block rewards)
  • Attacker gains are self-limiting: the double-spend value plus any block rewards earned, whose value tends to collapse if the attack undermines confidence

Example 37.2 (Cost Comparison)

Honest Miner Attacker
Revenue Block rewards + fees Double-spend value
Cost Hardware + electricity Hardware + electricity
Duration Ongoing One-time
Risk Market fluctuation Detection, prosecution, price crash

37.7 Social Layer Defenses

Definition 37.10 (Social Consensus)

Beyond technical rules, Bitcoin has social defenses:

  • User Activated Soft Fork: Users can reject miner misbehavior
  • Exchange monitoring: Detect and respond to attacks
  • Community coordination: Share attack intelligence
  • Emergency response: Coordinate defensive forks if needed

Remark 37.6 (The 2013 Fork Response)

When a bug caused a 24-block reorg in 2013:

  • Developers, miners, and businesses coordinated on IRC
  • Miners voluntarily downgraded to maintain consensus
  • Crisis resolved within hours
  • Demonstrated social layer's importance

37.8 Finality Considerations

Definition 37.11 (Probabilistic vs Deterministic Finality)

Probabilistic finality (Bitcoin):

  • Reversal probability decreases exponentially with confirmations
  • Never reaches zero (theoretically)
  • Practical finality after sufficient confirmations

Deterministic finality (some other systems):

  • Block is final after specific condition met
  • Cannot be reversed without breaking protocol
  • Often requires different consensus mechanism

Remark 37.7 (Practical Finality)

For practical purposes, Bitcoin transactions are "final" when:

  • Cost of reversal exceeds transaction value
  • Typically 6 confirmations for large amounts
  • Even fewer for amounts below attack cost threshold
